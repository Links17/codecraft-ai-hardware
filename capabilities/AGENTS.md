# Cloud Skill Capability rules

Capability contracts are consumed by cloud Skills. This directory is not a taxonomy of device peripherals: GPIO, display, audio, touch and similar native interfaces belong in Device facts and Target metadata.

Read [domain boundaries and Provider policy](../docs/architecture/capability-provider-policy.md) before changing contracts or Providers. The cloud domain MUST use neutral registry primitives and MUST NOT import or construct the hardware Catalog. Optional Target lookup MUST be injected by its caller. Keep stable operation semantics in Capability; service limits, billing and defaults belong in versioned Provider policy with pinned sources. Policy constraints MUST only narrow the Capability schema. Defaults require an explicit Capability annotation; archival MUST remain a caller decision. Review semantic contract, policy and Skill package versions independently. Never update a Skill fingerprint to accept unreviewed drift.

Define each Capability from an actual consuming Skill contract. Record its versioned input/output schema, configuration, resources, errors, limitations, dependencies and integration tests. Reference native Targets as implementation dependencies where needed. Do not introduce accounts, cloud runtime, a remote protocol or publishing infrastructure here. Do not invent Capability names or claim an integration is complete without a concrete consumer and executable tests. Host-only cloud discovery and preparation MUST work without Device/Target metadata. Explicit Target context MUST be validated and MUST NOT imply device integration. Provider skill.files MUST pin the complete standalone package, including binary assets; context, export and locks MUST preserve those files. Conformance tests MUST execute the prepared argument array through the actual isolated Skill against a local fixture and check response schema and failure exit status; --help alone is not integration evidence.
