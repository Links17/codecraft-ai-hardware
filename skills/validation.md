# Validation workflow

Run generate --check, validate --static, affected native Target/project builds, then validate for the complete software gate. The CLI is python3 codecraft.py.

Tests reject source contradictions, missing/cyclic dependencies, omitted cross-layer resources, empty/incorrect metadata, wrong adapter identity/case coverage and stale evidence. Source checks cover canonical metadata formatting, Python syntax, retained licensing/attribution, local links, README language pairs, forbidden engineering-document translations and private-key material. Native peripheral interfaces and cloud Skill Capabilities are tested at their respective owners. Physical writes are excluded. Missing tools remain not_run; unsupported simulations remain not_supported.

The static gate also verifies bundled cloud Skill fingerprints and CLI contracts, helper synchronization, and the imported nine-case offline protocol suite. Each client is tested after isolated installation against a loopback service; no real cloud credentials or paid API calls are used. Capability-owned tests drive metadata → prepare → standalone CLI → mock API → actual output schema/exit status, covering every operation and local/archived media. Regressions also require cloud-only resolution without a hardware catalog, reject malformed selections and extra installed files, isolate installed bytecode, and preserve pinned binary assets through context/export/lock/package.

Common Provider policy tests live in capabilities/_tests/test_policy.py and are included in the same host gate. They check independent policy/Capability versions, restrictive schema fragments, approved defaults, effective outputs and exported-lock drift. Capability-owned client tests also cover the current ASR audio boundaries, TTS text/default voice, image prompt/request size and LLM token defaults. The domain regression prohibits hardware Catalog imports while loading the cloud domain and checks the registry's native/cloud/export dependency closure. Synthetic policy variations are not a second real Provider or live billing evidence.

Standalone release tests live in skills/_cloud/tests/test_release.py. They verify identical candidate bytes, explicit version changes, real isolated candidate/client conformance, source/candidate drift rejection, transactional rollback and retained recovery backups. Public-entry tests check JSON, typed errors and exit codes, source-locked exports and explicit relocking. Reference validation rejects application roots; both the application build command and direct adapter builds check the current source lock and actual toolchain. Clean export checks preserve the requested example across every selected variant, and retained evidence must cover all native cases for that selection, including overlays. README/Skill/CI commands use python3 codecraft.py; repository-only release maintenance is not required by exported applications.

Test ownership and focused commands are specified in [the host testing guide](../docs/development/testing.md). The common runner recursively discovers owner-local modules, runs both plain functions and unittest cases, and exposes `python3 codecraft.py test --list` / `test --path <owner>`. Each protocol method and native case has an owner-qualified identity and runs directly through this runner.

ESP-IDF composition tests validate each example's selected BSP sources, local components, managed manifests and Target/export closure. Native builds also compare actual BSP source and requirement lists with the declared composition. Settle native dependency locks before final source fingerprinting; preserve explicit system requirements and board configuration when narrowing components. See [native composition rules](../docs/development/native-compositions.md). Component counts alone are not measurements of firmware size, build time or runtime resources.

Variant checks cover Device/Target identity, selected source closure, project/lock provenance, adapter case coverage and actual CMake/compile definitions. Physical support is aggregated per variant; unknown revision compatibility cannot promote support, and one assembly cannot certify another. Full Target builds include all declared variants. See [hardware variants](../docs/development/hardware-variants.md).
